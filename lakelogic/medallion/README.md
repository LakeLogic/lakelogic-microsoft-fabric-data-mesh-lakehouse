# Medallion mesh project (Microsoft Fabric)

Generated by the LakeLogic Medallion Builder for a **schema-enabled** Fabric
Lakehouse: schema-per-domain + a shared `quarantine` schema, a `_domain.yaml` →
`_system.yaml` → per-layer contract registry, a thin parameterised pipeline driver
(all logic in the OSS `lakelogic` engine — edit the contracts, not the notebooks),
dependency-aware Fabric Data Pipelines, and a `deploy.py` you run with your own
Fabric credentials.

## What's here

- `_contracts/{domain}/_domain.yaml` (domain defaults, inherited by every system
  below it) + `_contracts/{domain}/{system}/_system.yaml` — the contract registry
  (uc / schema-enabled mode). One dir per `(domain, system)`:
- `_contracts/internal/` — internal domain
- `_contracts/rideflow/` — rideflow domain
- `_contracts/stripe/` — stripe domain
- `_contracts/{domain}/{system}/contracts/{bronze,silver,gold}/*.yaml` — the
  canonical data contracts (never re-serialised — byte-for-byte from the approved,
  sealed design).
- `notebooks/pipeline_driver.ipynb` — one parameterised, **job-safe** runner
  (installs `lakelogic` with `pip --target` + `sys.path`, avoiding the pip-magic
  cell that cancels Fabric job sessions). Set `domain` / `system` / `environment`
  per run.
- `notebooks/00_setup.ipynb` — idempotent: **materialises the embedded `_contracts/`
  registry into `Files/ll_contracts`** (so a git-synced project needs no upload), then
  creates the domain + `quarantine` schemas and per-domain run-log tables. Run it first.
- `notebooks/90_synthetic_seed.ipynb` — writes a **contract-derived synthetic
  bronze estate** (schema only — no production rows read) as Delta tables directly in
  the lakehouse (`synthetic_<domain>` schema); see "Build a synthetic estate".
- `pipelines/{domain}_{system}.json` — one Fabric Data Pipeline per system (the
  `pipeline_driver` run once per present layer, bronze → silver → gold, chained on
  `Succeeded`); `pipelines/_mesh_orchestrator.json` — the wave-packed master orchestrator that
  runs every system pipeline in dependency order.
- `pipelines/_synthetic_seed.json` — runs the synthetic-seed notebook once per
  system to write your synthetic **bronze** estate as Delta tables — a customer-run,
  FK-consistent synthetic replica of your app estate, no production data copied.
- `deploy.py` — **you** run this (your Fabric creds); it uploads `_contracts/`,
  imports the notebooks, and creates/updates the pipelines via the Fabric REST API.
- `olc/` + `.github/workflows/validate-olc.yml` — the Open Lakehouse Contract
  verb layout and a CI Action that validates every contract on each PR.

## Run order — waves

The master orchestrator (`pipelines/_mesh_orchestrator.json`) runs the per-system
pipelines in **waves** of at most 2 (a parent system's contracts
consume another system's assets, so the parent lands in a strictly earlier wave).
Each wave waits on the whole previous wave:

- **Wave 0** — `internal/internal`, `rideflow/rideflow`
- **Wave 1** — `stripe/stripe`

## Run it — git-native (no deploy.py)

This project is in Fabric **git-integration** format. Connect your workspace to this
repo, then:

1. **Sync** — Workspace → **Source control** → **Update all**. The notebooks and
   pipelines appear as workspace items.
2. **Bootstrap** — attach a **schema-enabled lakehouse as the default**, then run
   **`00_setup`** once. It **materialises the sealed `_contracts/` registry into**
   **`Files/ll_contracts`** (embedded in the notebook — no upload, no creds), then creates
   the schemas + run-log tables. This is the step that makes the project self-contained:
   git sync brings items, not data files, so `00_setup` supplies the contracts every
   notebook reads.
3. **Stage (optional safety gates)** — run `pipeline_driver` with `dry_run="true"`
   (validate + resolve the DAG, nothing written), then `ddl_only="true"` (create tables,
   no data), then live.
4. **Run** — trigger a system pipeline to land + process data, or the mesh orchestrator for the whole mesh in one click.

Confirm each contract's `source.path` points at your landed data before the live
run — the exporter derived it from the scan's location evidence.

## Alternative: `deploy.py` (workspaces that aren't git-connected)

If you don't use git integration, `deploy.py` provisions + imports with YOUR creds:

1. `python deploy.py --workspace <ws> --lakehouse <lh> --setup-only` — provision,
   upload `_contracts/`, import the notebooks; run `00_setup` once.
2. **live** — `python deploy.py --workspace <ws> --lakehouse <lh> --invoke-connection <GUID>`
   builds the pipelines + the mesh orchestrator.

## Build a synthetic estate

Stand up a **safe, governed synthetic replica** of your application estate — a
FK-consistent copy for development, testing, demos and CI, with no production rows
copied:

1. **Seed** — run `pipelines/_synthetic_seed.json` (or `notebooks/90_synthetic_seed`
   directly). For every bronze contract it generates **contract-derived**, FK-consistent
   synthetic rows with the OSS `lakelogic` engine (`generate_related`; schema only — no
   production row is read) and writes each entity as a **Delta table straight into the
   lakehouse**, under a `synthetic_<domain>` schema in `Tables/`, every row stamped
   `_synthetic=true`.
2. **Use it** — query `synthetic_<domain>.<table>` immediately: develop, test, demo and
   onboard against a realistic copy of your estate. Deriving silver/gold on top by
   running the normal system pipeline is **optional** — the synthetic bronze stands
   alone.
3. **Realistic values (optional)** — set `generative=true` on the seed (with an LLM key
   configured in this workspace's environment) for AI-enriched, domain-appropriate
   values; it stays deterministic and FK-consistent, and falls back to the standard
   fakes if no provider is configured.

**Safe by construction:** shipping this project ships *definitions*, not rows —
the synthetic data only ever exists once **you** run the seed on **your** compute
(LakeLogic executes nothing). Everything it produces is **permanently synthetic**
(ADR-0011 decision 6): contract-derived fidelity (no distribution or value from
your production data informs the fakes), written to `synthetic_<domain>` schemas and
marked `_synthetic=true` — never re-classify it as production. Set `invalid_ratio` > 0
on the seed to inject bad rows if you later run the pipeline and want to prove your
quality gates quarantine them.
